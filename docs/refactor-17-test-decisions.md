# Refactor 17 — The decision for each test file

This page belongs to [Refactor 17](refactor-17.md), "Prune with each step", part "Tests".
The end of Stage A needs a decision for each test file. This page has one row for each
file in scope, with the outcome that the file checks and the decision by the table of the
plan.

## Scope

- Each Platform unit test file: 300 files under `services/platform/tests`, without the
  journeys in `tests/e2e`.
- Each commerce test file that imports a source file that Refactor 17 changed: 17 files
  under `services/commerce/tests`. The first Refactor 17 commit is `0ad79a20`.

## Result

| Decision                                                           | Files |
| ------------------------------------------------------------------ | ----: |
| Keep: the only check of an authorization, money or data outcome    |   249 |
| Keep: it asserts an outcome of product code, and no journey has it |    56 |
| Keep: one case for each distinct outcome of a fault                |    11 |
| Keep the file, delete one case                                     |     1 |
| Delete the file                                                    |     0 |

One case is deleted, in its own commit: "sets the band when the price is the one that was
shown" in `offer-price-allowance.test.ts`. Its one outcome assertion was a call to a mock
of the test. The journey `e2e/pi-commerce-actions.test.ts` applies a price allowance
through the real route and the real commerce engine, and reads the stored band.

The Platform unit suite had 301 files and 1,730 tests before. It has 301 files and 1,729
tests now.

## Why almost every file stays

Plan 92 removed the weak tests of this suite on 18 November 2026: 314 files and 1,816
tests became 302 files and 1,732 tests. This pass looked for what that sweep left.

- **Calls of a mock.** A script read each case of the 43 files that assert a call. Eight
  cases in three files assert only calls: `google-drive-picker`,
  `portal-provider-onboarding` and `commerce-lab/queue-projection-recovery`. In each one
  the call is the outcome: product code calls a callback of the page, or acknowledges a
  queue message. The test gives a function only to record it. They stay.
- **The shape of a module.** Nine files read a file as text. Each one reads a fixture, a
  SQL patch or the SQL statements of the source. `d1-split-statements.test.ts` reads the
  source, and it is a guard of the two-database boundary. No file asserts a list of
  exports or of imports.
- **An outcome that a journey has.** Six route files mock their stores heavily:
  `commerce-control-router`, `checkout-profile-control`, `counter-policy-control`,
  `counter-sale-control`, `access-control-mutation-route` and
  `commerce-offer-price-policy-route`. A search of the journeys for each error code that
  they assert found none of those refusals. They stay as the only check.
- **`environment-configuration.test.ts`** has one case that reads the Wrangler files and
  asserts the production Worker names and one database id. It is a guard of the deployed
  names, which must not change. It stays.

## Limits

- The decision "keep: the only check" does not prove that no journey has the outcome. A
  search for the error code, the route or the function ran for the files with mock
  signals, not for each of the 1,739 cases.
- Ten reader agents wrote the outcome text from the test titles and, for the files with
  mock signals, from the test bodies. I read each case that a script or an agent named as
  a delete candidate.
- The protected list of Plan 92 did not change. Its rows have a note in the table.
- No unit test was added, and no check moved to a journey.
